1. 결론 요약

현재 TFMS는 기능 자체는 안정적으로 동작할 가능성이 높지만, 누적 패치 구조로 인한 반복 감시 비용과 navigation wrapper 부채가 큰 상태입니다.

  • <script> 총 205개 (외부 3개 + 인라인 202개)
  • 인라인 JavaScript 202개 문법검사: 오류 0건
  • setInterval(...) 코드 위치: 15개

- 지속형 14개

- 사용자 동작 시에만 잠시 실행되는 임시형 1개 (v4589 transferFiles, 120ms × 최대 12회)

  • 지속형 Timer의 명목 호출 빈도: 약 13.1회/초
  • 이 중 버전 배지/URL을 다시 맞추는 lockVersion/forceVersion 계열이 약 11.2회/초 수준
  • new MutationObserver(...): 8개
  • popstate listener: 1개 — 정상
  • v4413 브라우저 history 안정화 이후에도 showPage/navTo를 수정하거나 hook하는 후속 script block: 약 45개
  • 최종 160ms 화면전환은 v4675에서 showPage를 1회 감싸는 구조로 유지됨

가장 중요한 판단: 지금은 Timer/Observer를 한꺼번에 줄이는 정리작업을 하면 안 됩니다. v47.11에서는 한 개씩, 기능 보존을 확인하면서 줄이는 방식이 안전합니다.

Timer 핵심 해석

setInterval 15개가 있다고 해서 15개 모두 문제인 것은 아닙니다. 특히 T6은 사용자 파일 전달 중에만 잠시 존재합니다. 문제는 지속형 14개 중 여러 개가 동일한 버전 문자열/URL을 반복 확인한다는 점입니다.

현재 성능/안정성 관점에서 가장 부담이 큰 것은 단순 Timer 개수보다 다음 조합입니다.

  1. 500~1000ms 주기의 전역 polling 다수
  2. lockVersion() 반복 실행 중첩
  3. 동일 페이지에 navigation hook + render hook + interval이 동시에 존재하는 구조

Observer 판단

현재 8개 Observer는 과거처럼 document.body 전체를 무제한 감시하는 형태가 주류가 아닙니다. 대부분 특정 DOM 노드에 좁게 묶여 있고 guard/debounce가 존재합니다.

따라서 Observer 8개를 숫자만 보고 줄이는 것은 권하지 않습니다. 특히 O5(v4616)와 O6/O7은 유지해야 할 가능성이 매우 높습니다.

4. Navigation 구조 진단

정상인 부분

  • 브라우저 뒤로가기/앞으로가기용 popstate는 1개입니다.
  • v4413의 historyNavDepth가 중복 pushState를 막습니다.
  • v4413은 의도적으로 showPage만 history wrapper로 감싸고, navTo는 showPage를 경유하도록 두었습니다.
  • 최종 v4675의 화면 전환은 160ms이고 MutationObserver를 쓰지 않습니다.

구조적 부채

정적 분석상 v4413 이후에도 약 45개 후속 script block이 showPage 또는 navTo를 다시 감싸거나 hook합니다.

이들은 대부분 다음 패턴입니다.

기존 navigation 호출
→ 특정 페이지면 setTimeout(...)
→ UI/필터/권한/렌더 재보정
→ 다음 wrapper 호출

현재는 정상 작동하지만 다음 위험이 있습니다.

  • 한 번의 메뉴 이동에 여러 개의 setTimeout이 연쇄 실행될 수 있음
  • 같은 페이지 진입 시 오래된 패치와 최신 패치가 차례로 실행됨
  • 새 wrapper를 추가할수록 호출 경로 추적이 어려워짐
  • 기능 문제 발생 시 어느 세대 wrapper가 원인인지 찾기 어려움

v47.11에서는 navigation wrapper를 통합하지 않는 것이 안전합니다. 이 작업은 사실상 v48.0 구조정리 범위입니다.

5. setTimeout 501개에 대한 해석

코드에서 setTimeout 문자열은 501회 발견되지만, 이것은 동시에 501개의 Timer가 실행된다는 의미가 아닙니다.

다수는 다음 성격입니다.

  • 페이지 초기화 후 [80, 250, 700, ...]ms 식의 한시적 recovery retry
  • 모달/렌더 완료 후 20~180ms 보정
  • 프린트 iframe 생성 후 일시적 위치 보정
  • 화면 이동 후 특정 페이지 UI 복구

따라서 setTimeout 501 → 100 같은 숫자 목표로 정리하면 오히려 회귀 위험이 큽니다.

향후 정리는 반복적으로 실행되는 watchdog부터 진행하는 것이 맞습니다.

7. 권장 다음 작업 — Stability Patch IV

Stability Patch IV — Today Fallback Watchdog Retirement

수정 범위는 v4585 today fallback interval 한 곳만으로 제한하는 것이 가장 안전합니다.

목표:

  1. v4589 Today Hub가 정상 구성되기 전에는 기존 v4585 fallback 유지
  2. v4589 Hub ownership이 확인되면 900ms fallback watchdog 종료
  3. v4585의 fallback renderer 코드 자체는 삭제하지 않음
  4. navigation/DB/권한/Today 데이터/최신 v4589 renderer는 수정하지 않음
  5. 회귀검사 후 setInterval 코드 위치 수 자체는 구현 방식에 따라 유지될 수 있으나, 런타임 지속 Timer는 14 → 13을 목표

이 작업은 성능 개선 폭은 크지 않지만 위험이 가장 낮은 첫 번째 Timer 정리입니다.

그 다음 순서는 v4585 page isolation polling 또는 v4607 Today UX polling 중 하나를 실제 동작 검증 후 선택하는 것이 좋습니다.

8. 최종 판단

TFMS v47.11은 현재 “불안정한 시스템”은 아닙니다. 오히려 기능 복구·권한·화면 안정화를 위해 여러 안전망이 누적된 시스템입니다.

다만 이제부터는 기능을 더 얹기보다 다음 원칙이 중요합니다.

  • 새 setInterval 추가 금지
  • 새 MutationObserver 추가 금지
  • 새 showPage/navTo wrapper 추가 금지
  • 기존 안전망을 한 번에 제거하지 않기
  • 한 패치 = 한 watchdog/한 충돌만 정리

이 원칙을 유지하면 v47.11을 운영 기준본으로 충분히 안정화한 뒤 v48.0 구조정리 단계로 넘어갈 수 있습니다.
