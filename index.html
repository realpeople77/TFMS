TFMS PRESENCE FEASIBILITY AUDIT

현재 접속자 현황 기능 적용 가능성 분석

기준본: TFMS v47.11 Operational Stable · 운영 HTML 수정 없음

결론: 적용 가능. 단, 1차 테스트는 “익명·가명 기반 접속자 수”로 시작하는 것이 가장 안전함.

1. 현재 구조와의 적합성

항목확인 결과판정
Supabase@supabase/supabase-js@2 사용. 공용 client를 getTfmsSupabaseClient()로 노출적합
로그인 상태cloudUser, cloudProfile, tfmsSession이 로그인 완료 후 설정됨적합
자동 로그인 복원auth.getSession() 기반 기존 흐름 존재적합
Auth 이벤트기존 코드에서 onAuthStateChange 사용 사례 존재충돌 위험 낮음
Realtime현재 channel(), Presence 사용 코드 없음신규 모듈 격리 가능
DB/RLSPresence 기본 테스트에는 신규 테이블·SQL 불필요변경 불필요

2. 가장 안전한 1차 구현안

① 로그인된 사용자만 기존 Supabase client로 Presence 채널 참가
② Presence payload에는 이름·부서·메뉴를 넣지 않음
③ 사용자 식별값은 SHA-256 가명값(user hash)으로만 전달
④ 관리자 화면에는 우선 🟢 현재 접속 N명만 표시
⑤ 로그아웃은 Auth SIGNED_OUT 이벤트에서 untrack/removeChannel 처리

동일 사용자가 탭을 여러 개 열어도 payload의 동일 user hash를 기준으로 중복 제거하여 “사람 수”로 계산할 수 있음. 채널 자체의 session key는 탭마다 고유값을 사용.

3. 실명 목록을 바로 넣지 않는 이유

Presence 상태는 같은 채널의 구독자에게 동기화된다. 따라서 UI를 관리자에게만 숨기는 것만으로는 실명 정보에 대한 실제 접근통제가 되지 않는다. 1차 테스트에서는 실명·부서 등 개인정보를 Presence payload에 넣지 않는 것이 안전하다.

4. 2차 확장안 — 관리자 실명 목록

Presence에는 가명 user hash만 유지하고, 관리자 브라우저에서만 기존 profiles 테이블을 조회하여 profile ID를 같은 방식으로 hash한 뒤 매칭한다. 이렇게 하면 Presence 채널에는 실명·부서가 흐르지 않는다.

단, 이 단계 전에는 현재 Supabase의 profiles SELECT RLS가 관리자 범위를 제대로 제한하는지 별도 확인이 필요하다. HTML만으로 RLS 정책 자체를 확정할 수는 없다.
